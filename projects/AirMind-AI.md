# AirMind AI: Urban Air Intelligence Operating System

> A mission-control console for city air quality: forecast pollution, explain what is driving it, plan and test interventions, and answer citizen and administrator questions with grounded, cited AI.

**Stack:** Python · FastAPI · XGBoost · scikit-learn · sentence-transformers · FAISS · Gemini · Supabase (Postgres) · React 18 · Vite · Leaflet · Recharts

---

## 1. Resume bullets (copy/paste)

- Built a **multi-horizon AQI forecaster** (16 direct XGBoost models, +3h to +72h) on 8,760 hourly rows of Delhi data. Predicting the log-change from the current value made it robust to a ~4× seasonal level shift. **It beats a persistence baseline by ~30% MAE at +1h and +6h** (95% CI [+22%, +36%] and [+21%, +33%]) and has lower RMSE than persistence at every horizon through 72h.
- Designed a **rigorous evaluation harness**: 4-fold expanding-window rolling-origin backtest, 14 methods compared (baselines and model variants), and moving-block-bootstrap confidence intervals on skill. It found that the previous recursive forecaster was **25–111% worse than persistence** at every horizon, and replaced it.
- **Diagnosed and fixed four data/ML pipeline bugs:**
  - an AQI conversion that returned 500 for fractional PM2.5, corrupting 96 training rows;
  - a database row cap (1,000 per request) that silently truncated training data to 1,000 of 2,737 rows;
  - a train/serve feature-index mismatch in the recursive forecaster;
  - non-idempotent backfill that duplicated rows.
- Built a **hybrid RAG pipeline** (MiniLM + FAISS dense search, BM25, reciprocal-rank fusion, cross-encoder rerank, Gemini) over 6 policy documents (1,048 chunks). On a held-out test split it lifted **hit@1 from 38% to 62% and MRR from 0.55 to 0.72** over dense-only retrieval, and a cross-encoder refusal gate (threshold chosen on a separate dev split) refuses **88% of out-of-scope questions** vs 62% for the cosine gate.
- Put the **evidence inside the product**: a "Model performance" panel on the Forecast screen (served by its own API endpoint) charts the model against baselines with confidence intervals, and shows the RAG before/after. Every number is generated by the evaluation scripts, none typed by hand.
- Shipped end-to-end: 7 product modules, 9 REST endpoints, FastAPI and React, live WAQI ingestion, OpenWeather historical backfill, Supabase storage and PDF report export. Every external dependency has a fallback, so the demo never breaks.

## 4. ML deep dive: the forecaster

### Data
- **8,760 hourly rows for Delhi** (22 Oct 2025 → 22 Oct 2026) from the OpenWeather Air Pollution history API, stored in Supabase.
- AQI is derived from PM2.5 using the CPCB National AQI breakpoints, on one consistent scale. Short gaps (≤6h) are interpolated.
- The backfill is idempotent and the history query paginates, so training sees all the data.

### Approach
- **Direct multi-horizon.** One XGBoost model per displayed step (3, 6, 9 … 24, 30 … 72h; 16 models). There is no recursive roll-out, so there is no compounding error.
- **Log-ratio target.** Each model predicts `log1p(AQI[t+h]) − log1p(AQI[t])` from scale-free features. Delhi AQI averages ~240 in winter but ~54 in the monsoon. A model trained on levels fails when the season changes, and the log-ratio target fixes this.
- **Features** (computed by one shared module used for training, serving and evaluation):
  - log of the current level
  - log-changes over 1, 2, 3, 6, 12, 24, 48 and 168 hours
  - 24h and 7-day rolling mean, std and max relative to now
  - hour-of-day (sin/cos) and day-of-week
  - PM2.5/PM10 and NO₂/PM2.5 ratios
- **Prediction intervals.** The 10th and 90th percentiles of held-out log-residuals, per horizon, applied around each forecast.
- **Anchoring.** The model outputs a ratio, so it is applied to the live reading shown in the UI. The forecast curve starts exactly at the dial.
- **Graceful fallback.** If there is no trained model or no fresh history, it serves an analytic projection and labels it as such.

### Evaluation protocol
- 4-fold expanding-window rolling-origin backtest: retrain per fold, never train on the future, test on later unseen periods.
- Metrics: MAE and RMSE per horizon, plus **skill vs persistence** with a moving-block bootstrap CI (block = 24h, to respect autocorrelation).
- Baselines and variants compared on identical origins:
  - persistence
  - seasonal-naive
  - hour-of-day mean
  - 24h moving average
  - diurnal-adjusted persistence
  - Ridge autoregression
  - XGBoost on levels (two feature sets)
  - XGBoost on residuals
  - XGBoost on log-ratio (shipped)
  - the original recursive forecaster
- **Ablation:** adding Open-Meteo weather covariates (wind, boundary-layer height, rain, humidity, pressure) did **not** improve accuracy with one year of history, so it is not in the product.

### Key engineering finding
The first evaluation showed the original model losing to a one-line baseline. Tracing it uncovered four pipeline bugs (Section 1). The model architecture was not the main problem. The data and the feature plumbing were.

## 5. RAG deep dive: the Copilots

```
question → dense search (MiniLM-L6-v2, 384-d, FAISS IndexFlatIP, top-30)
         + BM25 lexical search (top-30)
         → reciprocal-rank fusion → top-20 candidates
         → cross-encoder rerank (ms-marco MiniLM) → top-4
         → relevance gate (refuse if cross-encoder top-1 score < −2)
         → Gemini, prompted to use ONLY retrieved passages + live AQI readings
         → answer + sources + confidence + retrieved chunks
```

- **Corpus:** 6 documents, 1,048 chunks: CAQM GRAP (2022), CPCB National AQI, the WHO Air Quality Guidelines summary, NPCCHH health advisory, an air-quality indexes review, and a custom operational playbook. Chunks are 120 words with 25-word overlap.
- **Grounding:** every answer returns its sources, a confidence score and the retrieved passages. Below the relevance gate it refuses instead of guessing.
- **Live context:** current AQI, category and pollutant readings are injected so advice matches today's air, not a generic scenario.
- **Why hybrid + rerank:** MiniLM blurs exact terms ("Table 0.1", "N95", "GRAP IV"), which BM25 catches. A cross-encoder reads question and passage together, so it fixes the ordering. Retrieval got about 24 points better at hit@1 for ~1.0 s of CPU latency, which is small next to the LLM call.
- **Fallbacks:** hashed embeddings if MiniLM is unavailable, numpy cosine search if FAISS is unavailable, fused (un-reranked) order with a cosine gate if the cross-encoder can't load, extractive grounded answer if the LLM is unavailable.
- **Evaluation:** 48 in-scope and 16 out-of-scope labelled questions split into dev and test; strategy and gate threshold were chosen on dev, and results are reported on test (Section 2).

## 6. Engineering highlights

- **Architecture:** layered FastAPI backend (`api → services → agents → ai / rag → database`) with Pydantic schemas and pydantic-settings configuration; React 18 + Vite frontend with Recharts and React-Leaflet.
- **Data pipeline:** live WAQI ingestion, OpenWeather historical backfill (idempotent, de-duplicating), Supabase repository layer with pagination, and a repair script for the corrupted rows.
- **Reproducibility:** evaluation is one command per component, and both write a report to `docs/`.
- **Resilience:** `DEMO_MODE` runs the full product with zero API keys. Each of these fails over to a working fallback: embeddings, vector search, LLM, trained model, database and backend.
- **Reports:** one-click Commissioner brief exported to PDF.
- **Evidence in the UI:** `GET /api/forecast/performance` serves a small committed results file that the evaluation scripts regenerate, and the Forecast screen charts it. A generated offline copy keeps it working in demo mode.
- **Found by end-to-end testing:** while taking screenshots I saw the first Copilot question time out. Cold start (embedding model, cross-encoder, LLM) took longer than the frontend's 8 s limit. The fix: warm the models in a background thread at server startup and give the Copilot call a 60 s timeout. The next question after restart returns a grounded answer in about 12 s including the LLM.
- **Docs that can't drift:** `docs/forecast_evaluation.md` and `docs/rag_evaluation.md` are generated by the scripts and say which row is the shipped model.

### Reproduce the results
```bash
cd backend
python -m backfill --days 365        # idempotent history load
python -m ai.repair_aqi              # dry-run integrity check (add --apply to write fixes)
python -m ai.train_forecast          # trains the 16 direct models + intervals
python -m ai.evaluate_forecast       # → docs/forecast_evaluation.md
python -m rag.evaluate_rag           # → docs/rag_evaluation.md
python -m ai.performance_report      # rebuilds the dashboard's results file (the two scripts above also do this)
```

## 7. Interview prep: questions and answers

### The 60-second pitch
> "AirMind AI is an air-quality operating system for city administrators. It forecasts AQI up to 72 hours ahead, explains what is driving it, lets you test interventions, and has RAG assistants that answer from official policy documents and refuse when they don't know. The part I'm proudest of is the evaluation: I benchmarked the forecaster against baselines with a rolling-origin backtest, found it was losing to naive persistence, traced that to four data and pipeline bugs, and rebuilt it. It now beats persistence by about 30% at 1–6 hours with significant confidence intervals, and I report honestly that beyond 24 hours it only matches persistence on MAE."

### Forecasting and ML

**Q1. Which parts of the project use ML?**
Two parts use trained or learned models. The forecaster is a supervised XGBoost regression. The Copilots use RAG, with learned MiniLM embeddings and an LLM. Attribution, the intervention planner and the simulator are deliberately transparent rule-based models, because decision-makers need to audit them and there are no labelled source-contribution data to train on.

**Q2. Why XGBoost?**
It is strong on tabular features with a small to medium dataset, trains in seconds, gives feature attributions via TreeSHAP, and is easy to serve. With ~8.7k rows, a deep sequence model would likely overfit and wouldn't be easier to defend. I compared it against Ridge and simple baselines to show the added complexity is justified.

**Q3. Why predict a log-ratio instead of the AQI itself?**
Delhi's AQI averages roughly 240 in winter and about 54 in the monsoon, and I only have one year. With a level target, test folds in a new season were out of distribution, and the model even lost to persistence at 24h+. Predicting `log(AQI[t+h]) − log(AQI[t])` from scale-free features removes the level, so the model learns relative dynamics. That alone moved 24–48h results from clearly worse than persistence to level with it, and it made 1–6h significantly better.

**Q4. Why direct multi-horizon rather than recursive forecasting?**
Recursive forecasting feeds its own predictions back as inputs, so errors compound, and the original version needed hand-set clamps to stay believable. In my evaluation the recursive version was 25–111% worse than persistence. Direct models predict each horizon independently from real observations, so there is no error accumulation. The cost is 16 models instead of 1, which is cheap here.

**Q5. How did you evaluate it, and why that protocol?**
I used a 4-fold expanding-window rolling-origin backtest: train on the past, test on the next block, repeat. A random split would leak future information through autocorrelation. Each test fold is a season the model hasn't seen, so it is deliberately hard. I report MAE, RMSE and skill relative to persistence, with moving-block-bootstrap confidence intervals, because errors on consecutive hours are correlated.

**Q6. What baselines did you compare against, and why do they matter?**
Persistence, seasonal-naive, hour-of-day mean, 24h moving average, diurnal-adjusted persistence, Ridge autoregression, and several XGBoost variants. Persistence is the essential one: AQI changes slowly, so a model that doesn't beat "tomorrow equals now" adds no value. Without baselines my original 43.6 MAE would have looked like a model number rather than a red flag.

**Q7. What are your actual results?**
At +1h MAE drops from 3.33 to 2.33 (+30% skill, CI [+22%, +36%]). At +6h it drops from 14.2 to 10.2 (+28%, CI [+21%, +33%]). At 24, 48 and 72h MAE is level with persistence (CIs include zero), but RMSE is 9–11% lower, meaning fewer large misses. The honest summary is a strong short-horizon forecaster and a risk-reducing, not accuracy-improving, long-horizon one.

**Q8. Your 24–72h skill is ~0. Isn't that a failure?**
It is a data limitation, and I'd rather say so than hide it. Multi-day pollution episodes depend on weather such as wind and boundary-layer height, and on seasonal cycles. With one year of history there is only one example of each season. I ran an ablation adding real weather covariates from Open-Meteo, and it didn't help, since season and weather are confounded in a single year. The fix is more history, 2–3 years, not a more complex model.

**Q9. You mentioned finding bugs. Walk me through that.**
The saved model had MAE 43.6, which looked bad but plausible. I noticed hourly changes had a median of 2 points but a mean of 31, so a few huge spikes were dominating. Tracing them, every spike was exactly 500 at PM2.5 ≈ 30–31. My AQI converter had gaps between breakpoint bands (30|31, 60|61 …), so fractional values like 30.5 fell through and returned 500. That corrupted 96 rows. Looking at the data also showed the training query returned only 1,000 rows because of the database page cap, when the table held 2,737. I also found the recursive path used lags shifted by one step relative to training. I fixed all of them, repaired the rows with a dry-run-first script, and made backfill idempotent.

**Q10. How did you prevent data leakage?**
Time-ordered splits only, with training targets that end strictly before each test block. All features use information at or before the forecast origin. The same shared feature code is used in training, serving and evaluation so they can't drift, which is what caused the original index-shift bug.

**Q11. How do your prediction intervals work, and are they calibrated?**
For each horizon I take the 10th and 90th percentiles of the log-residuals on a time-ordered holdout and apply them around the point forecast, giving an 80% interval that widens with horizon. They are calibrated on that holdout, so coverage there is ~80% by construction. It is not an independent coverage test. A stricter check would calibrate on one block and measure on a later one.

**Q12. What do the features tell you?**
TreeSHAP on the level-feature XGBoost variant shows the current level and PM2.5 dominate, with the 24h rolling mean next and the 168h (one-week) lag also contributing. The weekly lag matters, which suggests a weekly activity cycle. Scale-free log-change features carry the same information in the shipped model.

**Q13. How would you improve the forecaster?**
First, more history (2–3 years) so seasons repeat in the training data. Second, archive real NWP forecast weather alongside AQI so the model sees what it would actually see at serving time, rather than reanalysis. Third, a multi-station spatial model. Fourth, quantile regression instead of residual-percentile intervals.

### RAG and LLMs

**Q14. Explain your RAG pipeline end to end.**
Documents are chunked into 120-word windows with 25-word overlap and embedded with MiniLM-L6-v2 into normalised 384-d vectors indexed in FAISS (inner product = cosine). At query time I run dense search and BM25 in parallel, fuse the two rankings with reciprocal-rank fusion, and rerank the top 20 with a cross-encoder to get the top 4. A relevance gate on the cross-encoder's top score decides whether to answer. If it clears the gate, Gemini is prompted to answer only from the retrieved passages plus the live AQI readings, and the response returns the answer, sources, confidence and chunks.

**Q15. How do you stop hallucination?**
Three layers. A relevance gate refuses when retrieval is weak. The prompt restricts the LLM to the retrieved passages and the live readings. And every answer exposes its sources and retrieved chunks so a user can check it. The gate is evidence-based: on a held-out test split, the cross-encoder gate refuses 88% of out-of-scope questions against 62% for the original cosine gate, at a 17% in-scope false-refusal cost. For comparison, a cosine gate tuned to the same 17% cost refuses only 75%.

**Q16. How did you evaluate retrieval, and what did you improve?**
I built 48 in-scope and 16 out-of-scope labelled questions, split into dev and test. A chunk counts as relevant if it comes from a gold document and contains a gold keyword. I compared dense, BM25, hybrid, and the rerank variants. On the test split, dense-only had hit@1 38% and MRR 0.55. Hybrid with cross-encoder rerank reached hit@1 62%, hit@4 83% and MRR 0.72. The cost is about 1 s of CPU latency per query.

**Q17. What are the limits of that evaluation?**
It's still small (24 test questions, 8 out-of-scope), so each question is ~4 points and small differences are noise. Relevance is labelled by keyword rules, not human judgement. I did fix the earlier problem of tuning on the reporting set: strategy and thresholds are chosen on dev, and I report test. The other remaining gap is that some factual queries, such as the WHO PM10 table value, still miss, because the answer sits in a table chunk with little prose.

**Q18. Why a score threshold rather than letting the LLM decide?**
It's cheap, deterministic and auditable, and it fails closed before any generation happens. LLM self-assessment of "do I know this?" is unreliable. The threshold is a measurable knob with a known precision/recall trade-off. I also compared two scores for it: cosine similarity and the cross-encoder logit. The cross-encoder separates answerable from unanswerable better (AUC 0.94 vs 0.91 on test), especially for near-domain questions like "best air purifier brand", which cosine similarity lets through.

**Q18b. Why hybrid search instead of just a better embedding model?**
The failures were on exact terms and numbers, such as "Table 0.1", "N95" and "GRAP IV", where lexical matching is strong and small embeddings are weak. BM25 plus dense fusion lifted hit@1 from 38% to 54%. The cross-encoder then added another 8 points, because it reads the question and passage jointly. A bigger embedding model would help too, but it wouldn't give the cross-encoder's re-ordering or its better refusal signal.

**Q19. What happens if the LLM or embedding model isn't available?**
Each layer degrades gracefully. No MiniLM: a deterministic hashed bag-of-words embedding keeps retrieval working. No FAISS: numpy cosine search with the same interface. No cross-encoder: the fused dense+BM25 order is used with the cosine gate. No LLM: an extractive answer composed from the live readings and the top retrieved passage. The user still gets a grounded response.

### Data, systems and design

**Q20. Is the data real?**
The live city feed, pollutant concentrations and station readings come from WAQI. The history used for training comes from OpenWeather's Air Pollution history API, which is modelled reanalysis-style data, not station measurements. I convert PM2.5 to a CPCB AQI myself, so the "AQI" is a single-pollutant index. The schools, hospitals, industries and construction layers on the map are reference data I curated, not live feeds.

**Q21. Why are attribution and the simulator rule-based? Isn't that just if-statements?**
Deliberately. There are no labelled source-contribution data to train a model against, so any learned attribution couldn't be validated. The rule-based version is transparent, each share traces to a measured pollutant, and it responds to live conditions. In an interview I describe it as explainable decision support, and say that with labelled data I'd move to receptor modelling such as PMF or CMB.

**Q22. How does the system handle failures?**
Every external dependency has a fallback: Supabase → local cache → seed data, trained model → analytic projection, MiniLM → hashed embeddings, FAISS → numpy, Gemini → extractive answer, backend → frontend mock layer. The UI states which path served the answer, for example the forecast label says whether it came from the trained model.

**Q23. How would you deploy and monitor the forecaster?**
Retrain on a schedule after the backfill job, and re-run the evaluation script as a regression gate so a new model must keep beating persistence before it ships. Monitor rolling MAE against persistence on live data, and alert on data freshness, since the serving path needs recent hourly history and falls back to the analytic projection if it's stale.

**Q24. What would you do differently?**
Build the evaluation harness first. I trained a model, saw MAE 43.6 and had no baseline to tell me it was broken. A persistence comparison on day one would have exposed the data bugs immediately. The second change is archiving weather forecasts from the start so I'd have the covariates to test properly.

**Q25. What is the one thing you want me to remember about this project?**
That I measured it honestly. I can tell you where it works (1–6h, +28–30% over persistence with significant confidence intervals), where it doesn't (24h+ on MAE), why, and what it would take to fix it.

### Product and engineering extras

**Q26. How do you show users that the model is any good?**
The Forecast screen has a "Model performance" panel. It charts the error of the previous model, the persistence baseline and the current model at each horizon, with skill and 95% confidence intervals, and marks the horizons where the model is only level with persistence. The numbers come from an API endpoint fed by the same scripts that write the evaluation reports, so the UI can't disagree with the docs.

**Q27. Tell me about a bug you found in your own change.**
After adding the cross-encoder reranker I took screenshots of the running app and the first Copilot question failed with a timeout. Unit-style evaluation had passed, but the cold start (loading MiniLM, the reranker and the LLM call) took longer than the frontend's 8-second limit. I fixed it by warming the retrieval models in a background thread at startup and raising the Copilot timeout to 60 s. The lesson: model quality metrics don't catch latency and integration problems, so I always run the real path end to end.

**Q28. What is the latency cost of reranking?**
About 1 second per query on CPU, against ~20 ms for dense search alone. It added 24 points of hit@1 and a better refusal signal. It's small compared with the LLM call, which is several seconds. If it mattered, I'd rerank fewer candidates (I use 20), cache common questions, or move the reranker to a GPU.

**Q29. Why does the 24h+ forecast show "≈ baseline" in the UI instead of hiding it?**
Because trust is the product. A forecast tool that overstates itself is worse than one that says where it is only as good as "same as now". The honest framing also makes the +1h and +6h gains more believable.

**Q30. If you had one more week, what would you do?**
Get 2–3 years of history and archive real weather forecasts alongside it, since that is what should unlock 24–72h skill. Then build a held-out, human-labelled RAG test set, add a table-aware chunker for numeric facts (the WHO guideline table is still a miss), and add monitoring that tracks live MAE against persistence.
